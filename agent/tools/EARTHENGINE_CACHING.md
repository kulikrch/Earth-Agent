# Кэширование EarthEngine MCP-инструментов

`agent/tools/EarthEngine.py` использует кэширование, чтобы ускорить повторные запуски и снизить количество обращений к Google Earth Engine. Это особенно важно при разработке и оценке benchmark-вопросов: одни и те же сцены, metadata и пиксельные данные могут запрашиваться многократно.

Кэширование не меняет методику анализа и не подменяет результат. Оно только позволяет повторно использовать уже полученные данные при совпадении параметров запроса.

## Зачем нужен кэш

Без кэширования каждый запуск заново обращается к Earth Engine:

- поиск сцен выполняется повторно;
- metadata скачивается повторно;
- pixel data запрашивается повторно;
- скачанные файлы пересоздаются;
- увеличивается время выполнения;
- растет риск упереться в rate limit или сетевую ошибку.

С кэшированием повторный прогон чаще использует уже полученные результаты. Это делает итерации быстрее и стабильнее.

## Уровни кэширования

В текущей реализации есть два уровня кэша.

| Уровень | Что кэшируется | Где хранится | Когда используется |
|---|---|---|---|
| Redis-кэш | Результаты `search_images`, metadata, pixel data NPY | Redis | До обращения к Earth Engine API |
| Файловый кэш | Уже сохраненные GeoTIFF-файлы | `TEMP_DIR` | До повторного скачивания файла |

## Redis-кэш

Redis используется, если установлен Python-пакет `redis` и доступно подключение к Redis-серверу. Адрес берется из переменной `REDIS_URL`. Если она не задана, используется значение по умолчанию:

```text
redis://localhost:6379
```

Если подключиться к Redis не удалось, инструменты продолжают работать без Redis-кэша. В stderr выводится предупреждение, но выполнение не прекращается.

### Что хранится в Redis

| Тип данных | Источник | TTL |
|---|---|---:|
| Search results | Ответы `search_images` | 1 день |
| Metadata | Ответы `get_image_metadata` / внутренней metadata-функции | 7 дней |
| Pixel data | Ответы Earth Engine `getPixels` в NPY-формате | 3 дня |

Ключи имеют вид:

```text
earthengine:<sha256>
```

Хэш строится из имени операции и параметров запроса. Например, для поиска учитываются коллекция, bbox, даты и порог облачности. Для pixel data учитываются image id, band name, bbox и resolution.

## Файловый кэш

Перед скачиванием канала инструмент проверяет, существует ли целевой GeoTIFF-файл в `TEMP_DIR`. Если файл уже есть, повторный запрос к Earth Engine не выполняется, а инструмент сразу возвращает:

```text
Result saved at <path>
```

Файловый кэш не имеет TTL. Он действует до тех пор, пока файл не удален вручную или не изменен `output_path`.

Важно: если файл с таким именем уже существует, инструмент считает его готовым результатом. Поэтому при изменении методики, bbox или resolution нужно использовать новый `output_path` или удалить старый файл.

## PNG-preview

После успешного создания GeoTIFF инструмент пытается создать PNG-preview рядом с `.tif` файлом.

Порядок backend-ов:

1. `matplotlib`, если установлен;
2. `Pillow`, если `matplotlib` недоступен;
3. если оба варианта недоступны или произошла ошибка, preview пропускается.

Отсутствие PNG-preview не означает ошибку скачивания GeoTIFF. Основной результат - `.tif` файл.

## Настройка Redis

Для локальной разработки достаточно запущенного Redis на `localhost:6379` и переменной окружения:

```text
REDIS_URL=redis://localhost:6379
```

Проверка подключения в PowerShell:

```powershell
.\.venv\Scripts\python.exe -c "import redis; r=redis.from_url('redis://localhost:6379'); r.ping(); print('Redis OK')"
```

Если Redis не нужен или временно недоступен, можно не запускать его. Инструменты будут работать без кэша.

## Управление Redis-кэшем

Посмотреть количество EarthEngine-ключей:

```powershell
redis-cli --scan --pattern "earthengine:*"
```

Очистить весь Redis database:

```powershell
redis-cli FLUSHDB
```

Удалить только ключи EarthEngine:

```powershell
redis-cli --scan --pattern "earthengine:*" | ForEach-Object { redis-cli DEL $_ }
```

В Windows PowerShell конвейер с `redis-cli` может зависеть от установленной версии Redis. Если команда не работает, проще очистить весь локальный database через `FLUSHDB`.

## Управление файловым кэшем

Файловый кэш находится внутри директории, переданной в `--temp_dir` при запуске EarthEngine MCP-сервера.

Удалить конкретный файл:

```powershell
Remove-Item -LiteralPath "evaluate_langchain\run\out\question_1\2022_ST_B10.tif"
```

Удалить содержимое выходной директории конкретного запуска:

```powershell
Remove-Item -LiteralPath "evaluate_langchain\run\out" -Recurse
```

Перед рекурсивным удалением нужно убедиться, что путь указывает именно на директорию артефактов запуска, а не на рабочий каталог проекта.

## Когда нужно очищать кэш

Кэш стоит очищать или обходить в следующих случаях:

- изменилась логика выбора сцены;
- изменился bbox, но используется тот же `output_path`;
- изменилось значение `resolution`, но используется тот же файл;
- нужно проверить, что агент действительно делает свежий запрос к Earth Engine;
- есть подозрение, что файл был создан старой версией инструмента;
- проводится контрольный прогон без переиспользования старых артефактов.

Кэш не обязательно очищать, если проверяется только логика Main Agent на уже полученных данных.

## Типовые сообщения в логах

| Сообщение | Смысл |
|---|---|
| `[INFO] Redis cache enabled: ...` | Redis доступен, кэш будет использоваться |
| `Warning: Redis connection failed: ...` | Redis недоступен, инструменты работают без Redis-кэша |
| `[INFO] Cache hit: earthengine:...` | Найдено значение в Redis |
| `[INFO] Cached: earthengine:...` | Ответ сохранен в Redis |
| `[INFO] File cache hit: ...` | GeoTIFF уже существует, скачивание пропущено |
| `[INFO] PNG preview created (...)` | PNG-preview успешно создан |
| `[WARN] PNG preview skipped ...` | Preview не создан, но GeoTIFF может быть корректным |

## Ограничения кэша

- Redis-кэш не знает, что в Earth Engine появились новые снимки после сохранения старого результата.
- Файловый кэш не проверяет, был ли файл создан с тем же bbox и resolution.
- При одинаковом `output_path` старый GeoTIFF будет переиспользован независимо от того, изменились ли параметры запроса.
- Кэш ускоряет повторные запуски, но может скрывать проблемы свежего получения данных.

Поэтому для финальных контрольных прогонов важно явно фиксировать, использовался ли кэш, или запускать проверку с очищенными артефактами.

## Практические рекомендации

- Использовать Redis во время разработки и повторных benchmark-прогонов.
- Сохранять разные вопросы и периоды в разные `output_path`, чтобы не смешивать файлы.
- Для проверки Data Acquisition Agent периодически запускать прогон с очищенным файловым кэшем.
- Для воспроизводимости сохранять логи вместе с результатами и выходными GeoTIFF-файлами.
- Не считать cache hit ошибкой: это нормальное поведение при совпадении параметров.
- При подозрении на устаревшие данные сначала очистить файловый кэш конкретного запуска, затем Redis-кэш.
